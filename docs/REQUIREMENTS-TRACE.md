## Known gaps, stated plainly

- Windows-only verification (installer, shortcuts, uninstall data-preservation,
  printer enumeration, packaged PDF) is executed by CI; its evidence is pasted
  into `docs/TEST-REPORT.md` after the first Windows run.
- DPI scaling and very large monitors are reviewed manually — there is no
  automated visual regression suite.
- The activation code is a good-faith local check. It is verified against a PBKDF2
  digest with constant-time comparison and machine binding, and the application
  says so on screen; a fully offline check cannot be made cryptographically
  strong, and nothing here pretends otherwise. The code itself appears in plain
  text in exactly two places — the developer's end-to-end driver
  (`tools/run-e2e.mjs`) and the stress-data seeder (`tools/seed-stress.mjs`),
  both of which have to _type_ it — and in the test fixtures that prove the
  screen accepts the right code and refuses the wrong one. The application
  itself, its bundle, and every shipped file carry the digest only.

## Post-merge release-blocker trace

Installed Windows normal GUI startup must not access Electron session before
`app.whenReady()`. The packaged CSP is registered before window creation;
`tools/ci/windows-check.ps1` launches the installed GUI without `--self-check`
and verifies its window and continued process life. Self-check remains a separate
path and cannot establish normal startup readiness. Release gate: pending Windows
CI and real-machine retest (see `RELEASE-AUDIT-v1.0.0.md`).
